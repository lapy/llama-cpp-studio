**Web UI assessment — 27 September 2026**

The UI provides substantial control over local inference, but requires users to understand too much of the underlying machinery before completing ordinary tasks. The highest-value work is protecting edits, communicating failures and runtime state accurately, and making common model operations easier to find.

**Scope and evidence.** Reviewed the Vue views, shared components, stores, styles, routing, and README. Inspected the actual frontend in Chromium at 1440px and 390px using controlled API fixtures because no backend was listening on port 8081. Covered a populated library, empty library, failed library request, Search, Engines, GGUF configuration, the Audio empty state, and the library in light mode. Checked configuration navigation with unsaved edits. This was not an end-to-end download, build, inference, or assistive-technology audit. Populated search results and audio inference were assessed from source rather than exercised. Existing backend work was left untouched.

The current design has useful foundations worth preserving: shared page components and tokens, responsive layouts, dark/light themes, explicit running states, task details and cancellation, configuration templates, command import/preview, URL-backed search filters, and an existing sticky configuration action bar. The apply dialog already distinguishes selective model changes from a proxy reload and explains their impact. Recommendations below extend these features.

| Priority | Improvement | Impact | Relative effort |
| --- | --- | --- | --- |
| P1 | Protect unsaved configuration | Prevent lost work | Small–medium |
| P1 | Separate failed requests from empty results | Restore trust and recovery | Small–medium |
| P1 | Repair keyboard access, control names, and contrast | Make core actions usable | Medium |
| P1 | Make saved versus running settings explicit | Prevent operational confusion | Medium |
| P2 | Add common configuration controls and hide advanced sections | Reduce setup effort | Medium |
| P2 | Add library search, filters, sorting, and a list view | Support growing collections | Medium |
| P2 | Guide first-run setup and reorder Engines | Shorten time to first working model | Medium |
| P2 | Consolidate background tasks into an activity panel | Reduce interruptions and improve recovery | Medium |
| P2 | Simplify discovery and token setup | Reduce search friction | Small–medium |
| P3 | Improve endpoint handoff, visual consistency, and UI regression coverage | Improve daily use and maintainability | Medium |

P1 means address before cosmetic redesign; P2 is the next workflow iteration; P3 can follow. Effort is comparative, not a delivery estimate.

**1. Protect unsaved configuration.** Browser-confirmed: entering custom arguments displayed “Unsaved changes”; clicking Models navigated immediately, without a confirmation; returning showed an empty arguments field. `ModelConfig.vue` tracks changes but has no route-leave or unload guard. Add Save / Discard / Stay for internal navigation, browser-close protection when dirty, and optional session draft recovery keyed by model and engine. Preserve the existing sticky action bar. Acceptance: edits survive canceled navigation, successful saving allows navigation, and a failed save keeps the draft.

**2. Distinguish empty, failed, and stale data.** Browser-confirmed: a 503 from `/api/models` rendered “No models downloaded yet.” `ModelLibrary.vue` has loading and empty branches but no persistent fetch-error branch; its initial `Promise.all` also precedes event subscriptions and polling setup. Show “Could not load models” with Retry; retain previously loaded rows with a stale-data indication on subsequent failures. Initialize recovery subscriptions independently of initial request success. Apply the same state model to Search and configuration loading. Do not present zero resource usage or offline status as verified facts while status is still unknown. Acceptance: outages never look like an empty library, and recovery does not require a full page reload.

**3. Complete accessibility at the custom-control boundaries.** Rendered configuration engine choices are `div` elements with `tabIndex = -1` and no interactive role. Replace them with a radio group or native buttons exposing selection state. Several rendered refresh, configure, delete, and back buttons have neither visible text nor an accessible label; add explicit names, including the affected model where useful. Audio task tabs have tab roles but lack the complete arrow-key/focus and panel relationships of the tab pattern. Associate labels with Search and Audio fields, retain Models as the active navigation section on model configuration, and add a skip link.

Light-mode engine tags retain the hard-coded pale `#bfdbfe` foreground in `ModelLibrary.vue`; they were visibly faint. Dark-theme muted text `#64748b` against surface `#2a3142` computes to approximately 2.73:1. Audit actual rendered foreground/background combinations, especially small metadata and gradient navigation buttons, and replace literal colors with theme-aware semantic tokens. No reduced-motion rule was found in frontend source. Follow [W3C keyboard guidance](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html), [contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), and the [ARIA tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/). These findings are not a full conformance verdict.

**4. Bring runtime state into the model workflow.** The project already supports saved changes, pending publication, selective restarts, and proxy reloads. However, the save toast only says “Configuration saved,” the global trigger says “Apply llama-swap config,” and most state explanations live in dialogs or technical tooltips. Add a compact model-level summary: Unsaved edits → Saved, pending apply → In use. Use the actual action as the primary label: “Use on next start,” “Restart this model,” or “Reload proxy.” Before a disruptive action, show the affected models and request impact. Keep filesystem names and revision details in an expandable technical view. Do not collapse saving and disruptive application into an ambiguous button.

**5. Make configuration discoverable without knowing flag names.** The current parameter workflow is search → add a tag → edit the parameter. That is useful for experts, but an initially empty parameter pane gives newcomers little guidance. Before reaching it, the page presents companions, stable IDs, API aliases, and sub-ID variants. At 390px, the sampled configuration page was approximately 3,256px tall even with an empty parameter pane. Add an engine-aware Basics section for commonly supported controls such as context size, GPU placement/offload, and concurrency; retain search and command import for advanced use. Group routing, environment, raw arguments, and command details into collapsed advanced sections. Show compatible engines first and offer “Show other engines” for the disabled choices. Clearly distinguish inherited defaults from explicit overrides and explain that removing a parameter resets it.

**6. Turn the library into an operational workspace.** `ModelLibrary.vue` renders the full set of groups without local search, sorting, or filters and expands all groups on mount. The desktop card grid wraps long repository names, repeats group/variant metadata, and exposes group-delete and variant-delete icons close together. Add local search, Running / Stopped / Needs attention filters, engine/task filters, and sorting by name, size, or recent use. Offer a compact row view with aligned model, variant, engine, size, status, and actions; keep cards as an option. Use visible Start/Stop and Configure actions where space allows, place deletion in an overflow menu, and show friendly names with repository IDs as secondary text. Preserve expansion state and avoid adding virtualization until collection size warrants it.

**7. Guide the first successful model launch.** The Models empty state sends users to Search without checking whether a compatible engine is available. The README describes a much longer setup sequence. Add a dismissible, state-aware checklist: choose task → prepare compatible engine → download model → review configuration → start → test/connect. Reuse existing readiness data rather than maintaining an independent setup state. On Engines, move the engine choices before routing; currently System and expanded Virtual models & profiles appear first. Separate Not installed, Installed but inactive, Active, Building, and Failed instead of relying on “No Active.” Offer a contextual Install or Activate action and a short explanation of which formats/hardware each engine supports. Keep advanced engine selection available.

**8. Make activity persistent and bounded.** `TaskNotifications.vue` renders all matching running/completed/failed tasks into a fixed tray with `z-index: 20000`, explicitly above dialogs. The tray has no explicit height bound. This is a source-confirmed risk of covering controls as tasks accumulate, especially on mobile; task-heavy layouts were not exercised. Introduce an Activity button with a running count and a scrollable panel containing progress, logs, failure reasons, cancellation, and supported retry actions. Limit transient notifications to a small number and avoid placing interactive notifications above modal dialogs. Keep failure details available after a toast disappears. Represent queued and canceled states explicitly where the backend supplies them.

**9. Reduce discovery friction.** Mobile Search fits the viewport, but format, engine, task, input, output, source, import, and the token warning occupy much of the first screen. Keep query and task prominent; put secondary filters behind a filter control with an active count and Reset. Retain existing URL persistence, compatibility evidence, recommended variants, and provider status. Explain download size separately from estimated runtime memory, and label resource estimates as estimates. The Search “Set token” action currently only routes to Models; open the token dialog directly or provide a real settings destination, then restore search context. Make the general missing-token message informational and dismissible while retaining a clear warning on gated results. Provider failures should remain visible even when no results are returned.

**10. Improve the handoff and visual system.** A running text model should offer “Connect” with the actual API model ID, endpoint, copyable request example, and a lightweight test action. Audio already has a first-class test workspace; text-model testing currently depends on the external llama-swap link or a client. On Audio, allow adding reference audio within the workflow rather than requiring a trip through Config → Assets. Use restrained active-state borders and badges, fewer glows, legible metadata, and consistent labels such as “Discover,” “Model library,” and “Pending changes.” The page still references the Vite favicon; replace it with project branding. Keep the existing four-item mobile navigation unless user testing demonstrates a need to restructure it.

**Implementation sequence and validation.** First deliver draft protection, truthful request states, keyboard/name/contrast fixes, and the token-dialog shortcut. Next deliver clearer configuration state, Basics/Advanced organization, library controls, and reordered Engines. Then add guided setup, Activity, and connection testing. Validate both themes and 390px/desktop layouts with real PrimeVue components; existing tests often stub controls and cannot establish rendered accessibility. Add focused browser coverage for edit navigation, failed fetch/retry, keyboard engine selection, apply-impact review, and task overlays. Track time to first successful model request, clicks to find/start an installed model, recovery after a failed operation, and accidental edit loss. Establish baselines before setting numeric targets.
